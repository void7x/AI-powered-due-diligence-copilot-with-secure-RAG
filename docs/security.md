# Security notes

## Authentication & tenancy
- Bearer access tokens are HMAC-SHA256 signed and short-lived; passwords are hashed with PBKDF2-HMAC-SHA256 using a per-password random salt.
- **Tenant isolation**: every company-scoped query filters by `company_id` and verifies the requesting user owns the company. Missing or unauthorized resources return `404` to reduce resource enumeration.
- Chat sessions, documents, risks, reports and jobs are scoped to the authenticated user/company context.
- Production-like environments require an explicit `SECRET_KEY`; development/tests can use an ephemeral or test-specific key.

## File uploads
- Extension + MIME allow-list: PDF, DOCX, PPTX, XLSX, CSV, TXT only.
- Size cap `MAX_UPLOAD_MB` (default 50 MB) is enforced before a file is persisted.
- Upload filenames are normalized and sanitized; stored filesystem names include a server-generated UUID prefix. Original names remain metadata.
- Files live in `UPLOAD_DIR` outside the web-served frontend. Downloads go through an authenticated endpoint that re-checks ownership.
- SHA-256 dedupe is performed per company to prevent redundant storage and processing.
- Production deployments can use Cloudflare R2 / S3-compatible storage through the storage abstraction.

## Prompt-injection defense
The RAG system prompt treats retrieved document content as untrusted *data* and explicitly tells the model to ignore instructions contained inside evidence. Evidence ids (`SOURCE_N`) are generated by the retrieval pipeline and mapped by the backend to real documents/pages.

## LLM boundaries
- Financial calculations are deterministic Python logic; the LLM is not the source of computed figures.
- Page/document provenance comes from backend evidence mapping rather than model-generated page numbers.
- Retrieval is always company-scoped, so one company's indexed evidence is not intentionally exposed to another company's requests.
- Offline mode can run extraction, deterministic analysis and extractive RAG without an external AI API.

## Data handling
- SQLAlchemy ORM is used for database access; application SQL is parameterized through the ORM/query builder.
- CORS is configurable (`CORS_ORIGINS`). Structured logs carry request ids and operational metadata rather than document payloads, tokens or API keys.
- SQLite is available for isolated local tests/dev; PostgreSQL + pgvector is the supported production database path.

## Deployment notes
- Never commit `.env`, production secrets, API keys or real customer documents.
- Disable `CREATE_DEMO_USER` and `SEED_DEMO_DATA` outside local/demo environments.
- Use `STORAGE_BACKEND=r2` (or another durable object-storage integration) when container/local filesystem persistence is not guaranteed.
